# Swift monorepo documentation pipeline (2025–2026)

- Recommended architecture: keep API reference generated from Swift source with DocC, keep human-authored guides in Markdown, and assemble both into one navigation shell; DocC itself compiles source comments plus articles/tutorials and exports a self-contained web app/archive ([Swift DocC overview](https://www.swift.org/documentation/docc/), [DocC distribution](https://www.swift.org/documentation/docc/distributing-documentation-to-other-developers)).
- `swift-docc-plugin` is the SwiftPM command plugin for libraries and executables; `swift package generate-documentation` builds all compatible targets, while `--target` scopes a build ([plugin README](https://github.com/swiftlang/swift-docc-plugin/blob/main/README.md)).
- For static hosting, pass `--transform-for-static-hosting` and a matching `--hosting-base-path`; the plugin documents this exact GitHub Pages pattern, and DocC explains the required URL-rewrite/static-file behavior ([plugin README](https://github.com/swiftlang/swift-docc-plugin/blob/main/README.md), [DocC distribution](https://www.swift.org/documentation/docc/distributing-documentation-to-other-developers)).
- Treat the DocC archive as a generated release artifact, not hand-edited site content, and publish it from CI; Swift’s distribution guidance explicitly recommends a CI workflow that rebuilds and copies the archive to the web server ([DocC distribution](https://www.swift.org/documentation/docc/distributing-documentation-to-other-developers)).
- Put guides under `/docs/user` and `/docs/developer`, with user docs explaining installation/workflows and developer docs explaining architecture, contributing, testing, and release operations; this is a navigation/ownership boundary rather than a DocC requirement, so enforce it in the Markdown site’s sidebar and links.
- A practical layout is `/docs/user/**` and `/docs/developer/**` for Markdown, `/docs/api/<Module>/` for transformed DocC output, and `/docs/cli/` plus `/docs/schema/` for generated artifacts; keep generated directories out of source review or clearly mark them as build output.
- Starlight/Astro is the strongest default when the monorepo wants a polished unified site: it accepts Markdown/MDX, supports nested content directories, validates frontmatter, and supports custom Astro routes ([Starlight pages](https://starlight.astro.build/guides/pages/), [Starlight authoring](https://starlight.astro.build/guides/authoring-content/)).
- MkDocs is the simplest Python/YAML choice for Markdown guides and can emit fully static HTML suitable for GitHub Pages or S3 ([MkDocs](https://www.mkdocs.org/)).
- Docusaurus is the common React/MDX choice when versioning, i18n, search, and plugin-driven customization matter; its own docs describe it as a static-site generator with built-in documentation features ([Docusaurus introduction](https://docusaurus.io/docs/)).
- Hugo is the fast Go-based choice for teams already using Go/templates or needing flexible large-site content pipelines; Hugo renders Markdown with Goldmark and deploys generated static files ([Hugo introduction](https://gohugo.io/about/introduction/), [Hugo content formats](https://gohugo.io/content-management/formats/)).
- There is no official “DocC + Starlight/MkDocs/Docusaurus/Hugo” integration standard: use one of these generators for `/docs/**`, publish DocC under a stable `/api/` route, and link or iframe/route between outputs; DocC’s supported contract is the archive/static-hosting interface ([DocC distribution](https://www.swift.org/documentation/docc/distributing-documentation-to-other-developers)).
- Generate CLI reference from the executable itself in CI rather than copying README help: Swift Argument Parser provides `swift package generate-manual` and its generated manual reflects the command hierarchy/options; current releases also document `--experimental-dump-help` JSON output ([ArgumentParser changelog](https://github.com/apple/swift-argument-parser/blob/main/CHANGELOG.md), [ArgumentParser README](https://github.com/apple/swift-argument-parser)).
- Prefer the generated man/manual output as the canonical CLI reference and optionally convert it to Markdown/HTML for the site; do not promise stable prose/formatting for raw `--help`, because Argument Parser explicitly says autogenerated help wording/formatting is not public API ([ArgumentParser README](https://github.com/apple/swift-argument-parser)).
- `Codable` describes encoding/decoding behavior but does not, by itself, generate a complete JSON Schema; use an explicit schema builder/macro or schema-conversion library, then encode the resulting schema with `JSONEncoder` and commit/publish the generated JSON as a checked artifact ([Swift JSON Schema](https://github.com/ajevans99/swift-json-schema)).
- Make schema generation a Swift executable/test target that imports the production Codable types, writes deterministic JSON, and fails CI on a dirty diff; this keeps the published schema tied to compilable types while making intentional breaking changes reviewable ([Swift JSON Schema](https://github.com/ajevans99/swift-json-schema)).
- Public API filtering is the safe default: DocC generates public symbols for libraries and internal symbols for executables unless configured otherwise ([swift-docc-plugin 1.4.0 release](https://github.com/swiftlang/swift-docc-plugin/releases/tag/1.4.0)).
- For a public site, set `--symbol-graph-minimum-access-level public` explicitly for every public/library target and avoid `--includeSPI`/synthesized-symbol options unless the site is an authenticated contributor reference; SwiftPM exposes access-level choices including public, package, internal, private, and fileprivate ([PackageManager SymbolGraphOptions.AccessLevel](https://docs.swift.org/swiftpm/documentation/packageplugin/packagemanager/symbolgraphoptions/accesslevel/)).
- For internal developer docs, use a separate CI artifact/site and set `--symbol-graph-minimum-access-level internal` (or `private` only deliberately); the plugin added this flag in 2024 and its current release documentation shows the command form ([swift-docc-plugin 1.4.0 release](https://github.com/swiftlang/swift-docc-plugin/releases/tag/1.4.0)).
- Keep public and internal DocC builds separate because access filtering is an input to symbol-graph generation and accidentally publishing the contributor archive is a data-exposure risk; Swift’s access-control guidance distinguishes public API from internal implementation ([Swift access control](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/accesscontrol/)).
- Add a PR documentation gate that runs Swift tests, DocC conversion with warnings-as-errors/URL checks where available, CLI generation, schema generation, and the Markdown-site build; add the same jobs to a tag-triggered release workflow so the published site is generated from the exact tagged commit.
- Concrete tag-based examples include [OpenSwiftUI’s documentation workflow](https://raw.githubusercontent.com/OpenSwiftUIProject/OpenSwiftUI/main/.github/workflows/documentation.yml), which triggers on semantic-version tag pushes and deploys a versioned DocC site, and [VersionedDocC’s reusable Pages workflow](https://raw.githubusercontent.com/DocCLab/VersionedDocC/main/.github/workflows/pages.yml), which checks out full tag history, builds the static artifact, and deploys it to Pages.
- Swift’s own DocC ecosystem demonstrates GitHub Pages static hosting for `swift-argument-parser`, `swift-docc-plugin`, and `swift-url`, confirming that transformed DocC archives work as repository-path sites ([Swift Forums static hosting examples](https://forums.swift.org/t/support-hosting-docc-archives-in-static-hosting-environments/53572/32)).
- Pin the Swift/Xcode toolchain and DocC plugin version in release CI, check out full tag history when building versioned docs, and publish immutable version paths plus a stable “latest” alias; VersionedDocC documents full-history checkout, cache fingerprints, and per-version artifacts ([VersionedDocC](https://github.com/DocCLab/VersionedDocC)).
