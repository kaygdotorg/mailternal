# iOS IMAP/SMTP client with optional relay wakeups — evidence memo

Research date: 2026-09-01. “Fact” means directly documented by the linked source; “Recommendation” is an architectural inference from those facts.

- **Fact — iOS suspension:** Most iOS apps are suspended in the background, and Apple’s documented background modes are limited; the `remote-notification` mode is specifically a signal that new content is available, not permission to keep an arbitrary IMAP socket alive. ([Apple: background execution modes](https://developer.apple.com/documentation/Xcode/configuring-background-execution-modes))
- **Fact — low-level sockets:** Apple DTS states that low-level networking stops once an app is suspended, while some high-level APIs—most notably background `URLSession`—continue; therefore a foreground-created IMAP IDLE/TCP connection is not a reliable always-on wake mechanism. ([Apple DTS: background TCP](https://developer.apple.com/forums/thread/717396), [Apple: background URLSession](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background%28withidentifier%3A%29))
- **Fact — IMAP real-time mechanism:** IMAP IDLE lets the server send unsolicited mailbox updates while the client remains in the selected mailbox; without IDLE, the client must poll. ([RFC 9051 §6.3.13](https://www.rfc-editor.org/rfc/rfc9051.html))
- **Recommendation — iOS sync:** Make the iOS app a direct IMAP/SMTP client while active, but use APNs as a best-effort wake hint and reconnect/sync over IMAP after wake; retain polling or user-open refresh as the correctness fallback because APNs delivery is not guaranteed. ([Apple: notification payload guidance](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/CreatingtheNotificationPayload.html), [Apple: APNs delivery behavior](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns?changes=_2_2_1))
- **Fact — hosted generic-IMAP push credentials:** An IMAP watcher must authenticate before it can access most mailbox commands, using `AUTHENTICATE` or `LOGIN`; a hosted generic-IMAP watcher therefore needs a continuing authorization usable for its own IMAP connection. ([RFC 9051 §§3.1, 6.2](https://www.rfc-editor.org/rfc/rfc9051.html))
- **Fact — “reusable password” is not mandatory:** OAuth access tokens can authenticate IMAP via XOAUTH2, and OAuth refresh tokens are long-lived credentials used to obtain new access tokens; thus hosted push requires reusable mailbox authorization, but it need not be the user’s reusable mailbox password. ([Gmail: XOAUTH2 for IMAP](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol), [RFC 6749 §§1.4–1.5, 6](https://www.rfc-editor.org/rfc/rfc6749.html))
- **Recommendation — hosted relay consent:** Treat a hosted generic-IMAP push service as having mailbox-read authority (password, app password, OAuth refresh token, or provider-specific equivalent); prefer least-scope OAuth where supported, encrypt credentials at rest, and provide revocation/deletion because a refresh token is itself a long-lived authorization credential. ([RFC 6749 §10.4](https://www.rfc-editor.org/rfc/rfc6749.html), [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009.html))
- **Fact — APNs signing boundary:** APNs accepts notification requests from a provider server authenticated by an Apple-issued provider certificate or a JWT signed with the vendor’s APNs private key; the request contains the device token and JSON payload. ([Apple: communicating with APNs](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/CommunicatingwithAPNs.html), [Apple: token-based APNs](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns))
- **Recommendation — Mac relay without vendor key:** Have the user-owned Mac relay watch IMAP IDLE, create an authenticated opaque E2E-encrypted wake object, and POST `{device token, ciphertext, metadata}` to a vendor HTTPS gateway; the gateway—not the Mac—adds the vendor APNs authorization and forwards the unchanged ciphertext, so the Mac never receives the vendor signing key and the gateway need not decrypt the wake object. This is an inference from APNs’s provider/payload split and the app’s cryptographic design, not an Apple-prescribed protocol. ([Apple: APNs provider API](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/CommunicatingwithAPNs.html), [Apple: payload limits/guidance](https://developer.apple.com/documentation/usernotifications/generating-a-remote-notification))
- **Fact — payload constraints:** Standard APNs payloads are limited to 4 KB, may be stored/coalesced/throttled, and Apple recommends using notifications as a signal to fetch data rather than carrying sensitive data; an encrypted wake payload must therefore stay small and be treated as a hint. ([Apple: generating remote notifications](https://developer.apple.com/documentation/usernotifications/generating-a-remote-notification), [Apple: creating payloads](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/CreatingtheNotificationPayload.html))
- **Recommendation — Mac relay trust model:** Give the Mac relay mailbox authority only; give the iOS app the decryption key; give the vendor gateway APNs authority only; authenticate Mac-to-gateway requests separately (device registration/session credentials) and bind ciphertext to account/device/sequence to prevent cross-device injection and replay.
- **Fact — browser push boundary:** Web Push gives the application server a push endpoint and client-held encryption keys, delivers to a service worker, and encrypts message contents for the user agent; Apple documents iOS 16.4+ Home Screen web apps using this model and Safari web push using VAPID. ([W3C Push API](https://www.w3.org/TR/push-api/), [Apple: web push](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers))
- **Fact — browser transport:** WebSockets are HTTP-upgraded `ws`/`wss` connections to a WebSocket server, not a browser-native raw IMAP TCP API. ([RFC 6455 §§1.2–3](https://www.rfc-editor.org/rfc/rfc6455.html))
- **Recommendation — future browser client:** Keep the mailbox watcher/relay boundary server-side for a browser client: the browser should use HTTPS APIs/WebSocket for foreground sync and Web Push for wake, while the vendor gateway can fan out platform-specific APNs/Web Push delivery; a user-owned Mac relay can remain an optional mailbox watcher, but it cannot be the browser’s direct raw-IMAP transport.
