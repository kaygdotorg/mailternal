# IMAP library choices for Mailternal

**Snapshot:** 2026-09-03. Repository metadata (tip commit, open-issue count, license, language) is from each repository's GitHub REST API; source/README/package claims link to the exact files and line ranges. “Last commit” means the default branch tip, not a release tag. The target is a native macOS 26, Swift 6, SwiftNIO client that must cover CONDSTORE/QRESYNC/IDLE/MOVE/LITERAL-/ENABLE/SPECIAL-USE/X-GM-EXT-1 across Gmail, Dovecot, iCloud and Exchange.

## apple/swift-nio-imap

**What it is and readiness.** The README describes IMAP4rev1 parsing/encoding into type-safe values, extensive common-extension support and SwiftNIO integration ([README](https://github.com/apple/swift-nio-imap/blob/main/README.md#L1-L10)). It explicitly says the library is “still in development phases and not ready to be used in production system yet” ([README](https://github.com/apple/swift-nio-imap/blob/main/README.md#L11-L14)). The repository's contribution contract requires a concise, tested patch and says API changes are hard after release ([CONTRIBUTING.md](https://github.com/apple/swift-nio-imap/blob/main/CONTRIBUTING.md#L53-L78)); it does not publish a separate named maintainer roster, so Apple ownership plus the active PR queue is the defensible maintainer description.

**Parser limits (the hard edge).** `IMAPDefaults.lineLengthLimit` is a public, hard-coded 8,192-byte constant ([IMAPDefaults.swift](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAPCore/IMAPDefaults.swift#L28-L39)). `ResponseParser.Options` defaults `bufferLimit` to 8,192, `bodySizeLimit` to unlimited, and `literalSizeLimit` to 4,096; it throws when the buffer or literal exceeds those options ([ResponseParser.swift](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAPCore/Parser/ResponseParser.swift#L100-L145), [same file](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAPCore/Parser/ResponseParser.swift#L200-L209)). Most importantly, `IMAPClientHandler` constructs `NIOSingleStepByteToMessageProcessor` with `maximumBufferSize: IMAPDefaults.lineLengthLimit` and exposes no initializer argument on `main` ([IMAPClientHandler.swift](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAP/Coders/IMAPClientHandler.swift#L39-L55)). This means Mailternal cannot safely choose a larger line/literal buffer while using upstream `IMAPClientHandler`; a fragmented response can hit the 8 KiB processor ceiling before a configured parser literal limit.

**Our upstream seam.** [PR #849](https://github.com/apple/swift-nio-imap/pull/849) is still open and titled “Allow configuring IMAP client line buffer size.” Its proposed branch changes the initializer to `maximumBufferSize: Int = IMAPDefaults.lineLengthLimit` ([PR branch source](https://github.com/kaygdotorg/swift-nio-imap/blob/mailternal/line-buffer/Sources/NIOIMAP/Coders/IMAPClientHandler.swift#L42-L55)). The PR description says it is intended to let consumers bound untrusted-server input, but its prose says “preserving the existing 1 MiB default” while both upstream `main` and the proposed source show 8 KiB. Treat the source as authoritative, and pin the fork until the upstream decision is made.

**Required extension coverage.** The maintained extension matrix explicitly lists CONDSTORE, QRESYNC, ENABLE, IDLE, LITERAL-, MOVE and SPECIAL-USE ([SupportedExtensions.md](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAPCore/NIOIMAPCore.docc/SupportedExtensions.md#L13-L46)). The same document says IDLE uses `Command/idleStart` and `CommandStreamPart/idleDone` ([lines 75-77](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAPCore/NIOIMAPCore.docc/SupportedExtensions.md#L75-L77)), describes MOVE and UID MOVE ([lines 163-165](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAPCore/NIOIMAPCore.docc/SupportedExtensions.md#L163-L165)), and documents Gmail `X-GM-EXT-1` capability, labels, message IDs and thread IDs ([lines 215-219](https://github.com/apple/swift-nio-imap/blob/main/Sources/NIOIMAPCore/NIOIMAPCore.docc/SupportedExtensions.md#L215-L219)). Thus it covers the requested wire vocabulary, including Gmail-specific attributes. Coverage is grammar/parser/encoder support: Mailternal still owns capability negotiation, provider quirks, UIDVALIDITY/QRESYNC fallback, local persistence, retries and synchronization policy.

**Async client-interface discussion.** The Swift Forums pitch (2026-07-23) proposes an additive `IMAPCommands` module with `IMAPConnection.withConnection`, `send(_:)`, structured-concurrency pipelining, and response `AsyncSequence`s; it says `NIOIMAP` remains the event-driven low-level interface and the proposal is draft PR #841 ([Swift Forums pitch](https://forums.swift.org/t/pitch-an-imperative-style-async-await-imap-client-for-swift-nio-imap/88479)). This could reduce adapter ceremony if accepted, but it does not change the parser limit or add Mailternal's sync semantics, so it is not a reason to delay the current adapter.

## Cocoanetics/SwiftMail

SwiftMail is a high-level IMAP/SMTP package that depends directly on `swift-nio-imap` ([Package.swift](https://github.com/Cocoanetics/SwiftMail/blob/main/Package.swift#L50-L79)). Its README claims mailbox, FETCH/STORE, special-use, APPEND, NAMESPACE, ESEARCH and APPENDLIMIT operations ([README](https://github.com/Cocoanetics/SwiftMail/blob/main/README.md#L9-L18)), but its own matrix is the critical evidence: `NIOIMAP` is marked capable while `IMAPServer` is marked ❌ for X-GM-EXT-1, ENABLE, CONDSTORE, LIST-EXTENDED, LIST-STATUS, LITERAL- and QRESYNC ([README](https://github.com/Cocoanetics/SwiftMail/blob/main/README.md#L21-L50)). MOVE, SPECIAL-USE, ESEARCH, APPENDLIMIT and IDLE are marked implemented, but that is not enough for Mailternal's incremental-sync and Gmail label contract. The README says Swift 5.9+ and broader older platform floors, while the manifest is authoritative for current builds: Swift 5.9 package tools and macOS 12/iOS 15/tvOS 15/watchOS 8/Catalyst 15 ([README](https://github.com/Cocoanetics/SwiftMail/blob/main/README.md#L143-L159), [Package.swift](https://github.com/Cocoanetics/SwiftMail/blob/main/Package.swift#L1-L32)). Use SwiftMail as a useful reference for higher-level ergonomics, not as Mailternal's protocol implementation.

## MailCore2

MailCore2's README describes an asynchronous Objective-C API for IMAP/POP/SMTP, with iOS and Mac support ([README](https://github.com/MailCore/mailcore2/blob/master/README.md#L1-L10)); it also documents build targets for Android, Windows and Linux ([README](https://github.com/MailCore/mailcore2/blob/master/README.md#L15-L30)). The SwiftPM manifest is a compatibility warning: it requires only Swift tools 5.3, declares iOS 9/macOS 10.10, and exposes a binary target whose URL is `MailCore2-2020-09-24.xcframework.zip` ([Package.swift](https://github.com/MailCore/mailcore2/blob/master/Package.swift#L1-L15)). The repo tip is newer because of maintenance/build changes, but the package product still points at that 2020 binary.

The C++ API does contain useful protocol machinery. `MCIMAPAsyncSession.cpp` sets `DEFAULT_MAX_CONNECTIONS` to 3 and enables concurrent folder access by default ([source](https://github.com/MailCore/mailcore2/blob/master/src/async/imap/MCIMAPAsyncSession.cpp#L45-L58)). `MCIMAPFetchMessagesOperation.cpp` calls `syncMessagesByUIDWithExtraHeaders` when a mod-sequence is provided and returns both modified/added and vanished messages ([source](https://github.com/MailCore/mailcore2/blob/master/src/async/imap/MCIMAPFetchMessagesOperation.cpp#L88-L116)); the Objective-C header explicitly says `vanishedMessages` is populated when the server supports QRESYNC ([header](https://github.com/MailCore/mailcore2/blob/master/src/objc/imap/MCOIMAPFetchMessagesOperation.h#L32-L43)). It has IDLE and MOVE operations ([headers](https://github.com/MailCore/mailcore2/blob/master/src/async/imap/MCIMAPAsyncSession.h#L19-L32), [IDLE](https://github.com/MailCore/mailcore2/blob/master/src/async/imap/MCIMAPAsyncSession.h#L163-L170)), and the low-level engine includes Gmail label/message/thread extension sources ([directory](https://github.com/MailCore/mailcore2/tree/master/src/low-level/imap)). These strengths do not offset the old prebuilt binary, Objective-C/C++ ownership and callback model, unclear GitHub SPDX classification (API reports “Other”), or 233 open issues. The checked-in `LICENSE` is BSD-style ([LICENSE](https://github.com/MailCore/mailcore2/blob/master/LICENSE#L1-L18)); verify licensing with counsel before redistribution because GitHub reports `NOASSERTION` rather than an SPDX identifier.

## LibEtPan (C)

LibEtPan describes itself as a portable C framework for IMAP, SMTP, POP and NNTP, with RFC822/MIME parsing/building ([README](https://github.com/dinhvh/libetpan/blob/master/README.md#L1-L18)). Its SwiftPM manifest is not a Swift wrapper: it compiles a long list of C and Objective-C sources, links CFNetwork/CoreFoundation/Foundation/Security/curl/json-c/zlib, and declares macOS 10.13/iOS 12 ([Package.swift](https://github.com/dinhvh/libetpan/blob/master/Package.swift#L1-L16), [source list](https://github.com/dinhvh/libetpan/blob/master/Package.swift#L18-L130)). That makes an FFI integration technically possible but operationally expensive.

Coverage is unusually broad for a C alternative: the extension registry includes UIDPLUS, QUOTA, NAMESPACE, Gmail X-GM labels/message/thread IDs, ENABLE, CONDSTORE and QRESYNC ([mailimap_extension.c](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/mailimap_extension.c#L44-L80)); public headers expose `mailimap_enable`, `mailimap_idle`/`mailimap_idle_done`, QRESYNC fetch helpers and MOVE ([enable.h](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/enable.h#L42-L48), [idle.h](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/idle.h#L39-L58), [qresync.h](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/qresync.h#L51-L73), [mailimap.h](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/mailimap.h#L240-L260), [xgmlabels.h](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/xgmlabels.h#L36-L66)). No `SPECIAL-USE` or `LITERAL-` implementation appears in the checked-in IMAP extension registry/source search; treat those as gaps requiring raw command work and test evidence, not assume they are supported.

The parser has an explicit `MAILIMAP_LITERAL_SIZE_MAX (64U * 1024U * 1024U)` and rejects larger literals ([mailimap_parser.c](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/mailimap_parser.c#L6289-L6338)). GitHub reports `NOASSERTION` for license; source headers carry the project's BSD-like redistribution terms ([header example](https://github.com/dinhvh/libetpan/blob/master/src/low-level/imap/xgmlabels.h#L1-L28)). LibEtPan is a plausible C fallback, but bridging callbacks, ownership, event-loop behavior, TLS and error semantics into Swift 6 is a new subsystem, not a drop-in replacement for NIOIMAP.

## rust-imap (Rust via FFI)

The upstream crate is Rust `3.0.0-alpha.15`, edition 2021, dual Apache-2.0/MIT, and supports native-tls or rustls features ([Cargo.toml](https://github.com/jonhoo/rust-imap/blob/main/Cargo.toml#L1-L30)). Its README says it supports RFC 3501 and extensions, but explicitly says “This crate is looking for maintainers” ([README](https://github.com/jonhoo/rust-imap/blob/main/README.md#L10-L24)). The public API is synchronous (`ClientBuilder::connect`, login, `Session`), although it exposes `run_command`/`run_command_and_read_response` for raw commands ([client.rs](https://github.com/jonhoo/rust-imap/blob/main/src/client.rs#L1456-L1489)). IDLE is implemented as a blocking handle with a 29-minute refresh recommendation ([idle.rs](https://github.com/jonhoo/rust-imap/blob/main/src/extensions/idle.rs#L19-L53)).

Its parser types understand QRESYNC/VANISHED and Gmail labels ([unsolicited_response.rs](https://github.com/jonhoo/rust-imap/blob/main/src/types/unsolicited_response.rs#L124-L140), [fetch.rs](https://github.com/jonhoo/rust-imap/blob/main/src/types/fetch.rs#L229-L241)), and its session has explicit MOVE/UID MOVE methods ([client.rs](https://github.com/jonhoo/rust-imap/blob/main/src/client.rs#L1014-L1046)). However, there is no Swift module, Apple platform declaration, or native Swift concurrency surface. FFI would add Rust runtime/toolchain, C ABI ownership, cancellation and cross-language error mapping while leaving Mailternal to implement capability negotiation and sync policy. It is therefore not a better choice than NIOIMAP for this app.

## Provider protocol alternatives (fast paths, not universal replacement)

These are provider-specific alternatives to generic IMAP and should be selected only after account/provider detection. They cannot replace Dovecot or iCloud IMAP coverage.

### JMAP

JMAP Core is an IETF Standards Track protocol designed for mail/calendar/contact synchronization, optimized for mobile/web, with batched calls, push and delta updates ([RFC 8620 §1](https://www.rfc-editor.org/rfc/rfc8620.html#section-1)). JMAP Mail defines mailbox/thread/email data models, `Email/changes`, query/queryChanges, labels/keywords and push notifications; unlike IMAP, an email ID does not change when moved between mailboxes and an email may be in multiple mailboxes ([RFC 8621 abstract and §1](https://www.rfc-editor.org/rfc/rfc8621.html#section-1)). Implementing JMAP for a provider that advertises a JMAP Session is attractive because it models Mailternal's local sync directly, but discovery and availability must be capability-driven; there is no universal JMAP endpoint for Gmail, Exchange or iCloud in the cited standards.

### Gmail API

Google's official Gmail API overview says the API is RESTful, accesses Gmail mailboxes and sends mail, and is suitable for extraction/indexing, organization and other mailbox applications ([Gmail API overview](https://developers.google.com/workspace/gmail/api/guides)). The same page models labels, messages, threads and drafts as first-class resources. Push is provided by Gmail `watch` through Cloud Pub/Sub; notifications carry a mailbox `historyId`, and clients call `history.list` to obtain changes ([Gmail push guide](https://developers.google.com/workspace/gmail/api/guides/push)). A Gmail fast path preserves labels/thread identity and avoids IMAP's X-GM translation, but it requires Google OAuth scopes, Pub/Sub infrastructure and watch renewal at least every seven days; the guide also warns that notifications can be delayed/dropped and recommends periodic history fallback.

### Microsoft Graph

Microsoft's official Outlook mail API documentation says Graph provides authorized access to personal/organization Outlook mail and supports primary and shared Exchange Online mailboxes; it does **not** support in-place archive mailboxes ([Graph mail overview](https://learn.microsoft.com/en-us/graph/api/resources/mail-api-overview?view=graph-rest-1.0)). Graph's message delta API returns added, deleted and updated messages and uses `@odata.nextLink`/`@odata.deltaLink` state tokens to maintain a local folder store without refetching everything ([message delta](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0)). The overview also documents webhook change notifications for messages. Graph IDs can change after copy/move unless immutable IDs are requested, so the adapter must not treat ordinary message IDs like stable IMAP UIDs. This is a strong Exchange fast path, but it requires Microsoft identity/permissions and does not cover arbitrary Exchange/on-premise or iCloud accounts.

## Recommendation, risks and mitigations

**Recommendation:** Keep `apple/swift-nio-imap` as Mailternal's generic IMAP wire layer. It is the only evaluated Swift-native option whose maintained extension matrix covers every named requirement, and it already matches the SwiftNIO architecture. Do not adopt SwiftMail as a replacement because its high-level `IMAPServer` explicitly leaves the critical sync/Gmail/literal features unimplemented. Do not add MailCore2 or a Rust/C FFI for the generic path: each introduces ABI/ownership/build risk and still leaves provider and synchronization policy to Mailternal. Add provider fast paths behind the same account capability interface: Gmail API for Gmail, Graph for Exchange, and JMAP only when a server advertises a JMAP Session.

**Concrete risks of staying on NIOIMAP and mitigations:**

1. **Production-readiness disclaimer and API churn.** The README says not production-ready and there are 20 open issues. *Mitigation:* pin a reviewed commit/fork, keep Mailternal's `IMAPTransport` adapter narrow, maintain protocol fixtures against Gmail/Dovecot/iCloud/Exchange, and upstream fixes in small PRs.
2. **8 KiB handler buffer is hard-coded upstream.** Parser options alone do not change `NIOSingleStepByteToMessageProcessor.maximumBufferSize`. *Mitigation:* use the `mailternal/line-buffer` fork/PR #849, pass an explicit bounded maximum, and add fragmented-literal tests; do not silently raise it without a memory budget.
3. **Default body size is unlimited and literal default is only 4 KiB.** A hostile server can advertise large response bodies; a too-small literal limit rejects legitimate provider data. *Mitigation:* set explicit body/attribute/literal limits in Mailternal, stream bodies to storage, and map `PayloadTooLargeError` to a recoverable sync failure.
4. **Wire coverage is not sync semantics.** NIOIMAP parses QRESYNC/CONDSTORE and Gmail data but does not decide UIDVALIDITY resets, QRESYNC fallback, retries, folder scheduling or conflict policy. *Mitigation:* keep those in Mailternal's sync engine and test each capability against live/provider fixtures; treat capability advertisements as gates, never guarantees.
5. **Provider divergence and push lifecycle.** Provider capability divergence (the SwiftMail README matrix itself shows different Gmail/iCloud/Dovecot/Exchange rows), and IDLE is scoped to the selected mailbox ([RFC 2177](https://www.rfc-editor.org/rfc/rfc2177.html)). *Mitigation:* capability-probe every session, implement a UID FETCH/SEARCH fallback, rotate IDLE connections before server timeouts, limit connection pools, and prefer Gmail/Graph/JMAP fast paths where authorized.
6. **Upstream async interface is only a pitch.** The 2026 `IMAPCommands` discussion is draft PR #841 and additive, not a compatibility promise. *Mitigation:* do not block current work on it; evaluate after merge/release and keep the low-level adapter boundary so migration is mechanical.
