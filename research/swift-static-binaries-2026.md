# Swift static binaries (checked 2026-08-31)

- **Linux feasibility:** Yes—Swift’s official Static Linux SDK produces fully statically linked ELF executables with no external runtime or C-library dependency, using musl and depending only on the Linux syscall ABI: [Swift.org Static Linux SDK guide](https://www.swift.org/documentation/articles/static-linux-getting-started.html).
- **Portability trade-off:** The SDK forbids dynamic linking entirely (including `dlopen`), cannot use system libraries, and requires every non-bundled C/C++ dependency to be supplied and statically linked: [Swift.org guide](https://www.swift.org/documentation/articles/static-linux-getting-started.html).
- **Supported targets:** The official guide demonstrates x86-64 (`x86_64-swift-linux-musl`) and ARM64 (`aarch64-swift-linux-musl`) static outputs: [Swift.org guide](https://www.swift.org/documentation/articles/static-linux-getting-started.html).
- **Cross-compilation from macOS:** Yes; Swift’s SDK model explicitly supports building Linux binaries from macOS, but macOS builds must use the matching open-source Swift toolchain—not the Swift toolchain shipped inside Xcode: [Swift.org guide](https://www.swift.org/documentation/articles/static-linux-getting-started.html), [Swift SDK Generator](https://github.com/swiftlang/swift-sdk-generator).
- **Foundation support:** The official guide says packages using Foundation or SwiftNIO should work; non-Darwin builds use Swift Corelibs Foundation, while `FoundationNetworking` is a separate module for APIs such as `URLSession`/`URLRequest`: [Swift.org guide](https://www.swift.org/documentation/articles/static-linux-getting-started.html), [swift-corelibs-foundation](https://github.com/swiftlang/swift-corelibs-foundation).
- **Foundation limitation/history:** Static-musl Foundation networking had real toolchain-era issues—missing autolink arguments could cause SSL/ICU/zlib link failures, and a 2024 report found `URLSession` runtime failure; fixes landed in subsequent Corelibs Foundation work, so validate the exact Swift/SDK release: [issue #5089](https://github.com/swiftlang/swift-corelibs-foundation/issues/5089), [issue #5092](https://github.com/swiftlang/swift-corelibs-foundation/issues/5092), [Corelibs Foundation 6.1 release notes](https://github.com/swiftlang/swift-corelibs-foundation/releases).
- **Binary-size expectation:** Swift does not publish a single guaranteed size; official docs only state static executables are larger because runtime/dependencies are included: [Swift.org guide](https://www.swift.org/documentation/articles/static-linux-getting-started.html).
- **Observed sizes:** A 2024 Swift Forums report measured a stripped static-musl Hello World at about 5.9 MiB, while a 2025 report measured about 5.9 MiB for dependency-free Hello World and about 53 MiB for a small `swift-argument-parser` CLI; these are workload/toolchain measurements, not promises: [Swift Forums size report](https://forums.swift.org/t/build-helloworld-with-static-linux-sdk-on-macos/82906), [Swift Forums large-binaries report](https://forums.swift.org/t/using-the-static-linux-sdk-produces-very-large-binaries/75583).
- **Release/stripping:** Use release optimization and explicitly strip symbols (for example, `-Xlinker -s`) when size matters; the forums measurements show debug/unstripped artifacts can be tens or 100+ MiB: [Swift Forums size report](https://forums.swift.org/t/build-helloworld-with-static-linux-sdk-on-macos/82906), [Swift Forums large-binaries report](https://forums.swift.org/t/using-the-static-linux-sdk-produces-very-large-binaries/75583).
- **Current-release caution:** The Swift issue tracker still contains SDK-specific reports—for example, a Swift 6.3 `aarch64-swift-linux-musl` release-mode `async let` crash report—so test concurrency-heavy production workloads on the exact target architecture and SDK: [Swift issue #88750](https://github.com/swiftlang/swift/issues/88750).
- **macOS “single static binary”:** No—not fully static; Apple’s Swift.org documentation says no static SDK exists for Apple platforms because Darwin system calls must go through `libsystem.dylib`, so a macOS CLI will retain system dynamic-library dependencies: [Swift.org guide](https://www.swift.org/documentation/articles/static-linux-getting-started.html), [Apple Dynamic Libraries](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/DynamicLibraries/100-Articles/OverviewOfDynamicLibraries.html).
- **macOS shipping model:** A Swift CLI can still be shipped as one executable file if its non-system third-party code is statically linked; it is “single-file” distribution, not a 100% self-contained/static executable, because macOS loads `dyld` and dependent system libraries: [Apple Dynamic Libraries](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/DynamicLibraries/100-Articles/OverviewOfDynamicLibraries.html), [Apple compiling on macOS](https://developer.apple.com/library/archive/documentation/Porting/Conceptual/PortingUnix/compiling/compiling.html).
